## 二、经验教训

### 教训1: 比特语义一致性 ⚠️ 严重
**问题**: 通道比特=1 表示"有路可走"，但 `has_wall()` 把它当成了"有墙"。修改绘制逻辑后忘改移动逻辑，导致能走出地图但走不进去。

**规则**: 修改迷宫系统的任何一处比特逻辑时，必须 grep 全项目检查所有关联位置：
- `has_wall()` — 移动检测
- `_draw_cells()` — 墙壁绘制
- `_count_openings()` — 开口计数
- `_validate_path()` — 通达性验证
- 边界处理

### 教训2: 重构不能删除已有函数 ⚠️ 严重
**问题**: 并行 agent 修改同一文件时，UI agent 重写 `_draw_hud()` 把 `_draw()` 等8个绘制函数全部删除。

**规则**: 修改文件前必须 `grep -n "^func "` 列出所有函数，修改后验证所有函数仍存在。

### 教训3: 并行 agent 同一文件冲突
**问题**: 多个 agent 同时修改 main.gd，互相覆盖。

**规则**: 并行任务应分配不同文件。必须修改同一文件时，串行执行。

### 教训4: 测试必须匹配游戏实际逻辑
**问题**: Python 测试没考虑地图边界，验证通过但实际游戏起终点被边界墙卡住。

**规则**: 测试逻辑必须与游戏引擎逻辑完全一致（边界、比特语义、渲染顺序）。

### 教训5: 用户指导优于AI假设
**问题**: 递归回溯算法生成的迷宫死路太多，AI尝试多种后处理修复均不理想。用户一句"先画主路再加岔路"直接解决问题。

**规则**: 遇到反复失败的设计问题时，先向用户确认方向再动手。

### 教训6: BFS在空网格上无法寻路 ⚠️ 严重
**问题**: 用BFS在空网格上找路径，但BFS依赖已有通道（`grid[y][x]&d`），空网格全为0，BFS找不到任何邻居。

**规则**: 空网格上的路径规划不能用BFS，必须用确定性走法（先横后竖）直接打通。

### 教训7: 删除缓存文件导致全局class_name失效 ⚠️ 严重
**问题**: 删除 `.godot/global_script_class_cache.cfg` 后，headless模式不会自动重建，导致所有 `class_name` 类型找不到。

**规则**: 永远不要删除 Godot 缓存文件。如果必须重建，在 Godot 编辑器中打开项目（非headless）触发重建。

### 教训8: 新功能优先创建独立模块
**问题**: 在 main.gd 上反复添加功能（背包、UI面板），导致文件膨胀到810行。

**规则**: 新功能优先创建独立 .gd 文件，通过组合/信号与主文件交互。main.gd 应保持在500行以内。

### 教训9: Godot编辑器嵌入运行会遮挡游戏
**问题**: 编辑器的顶部菜单栏、底部输出面板覆盖了游戏视口。

**规则**: 在 project.godot 中设置 `window/size/override_controls_size=true`，强制游戏在独立窗口运行。

### 教训10: 并行agent修改同一文件必须串行
**问题**: UI agent和功能agent同时修改main.gd，互相覆盖了函数定义。

**规则**: 并行任务应分配不同文件。必须修改同一文件时，等待前一个agent完成后再修改。

## 五、需求提报规范

### 需求格式

```markdown
### [编号] 需求标题

**描述**: 一句话说明要做什么
**用户故事**: 作为[角色]，我希望[功能]，以便[价值]
**验收标准**:
- [ ] 标准1
- [ ] 标准2
- [ ] 标准3
**技术约束**: [引擎/性能/兼容性限制]
**依赖**: [前置需求编号]
**估时**: [S/M/L/XL]
```

### 示例

```markdown
### G-03 困难模式选择

**描述**: 在游戏开始前提供简单/普通/困难三个难度选项
**用户故事**: 作为玩家，我希望能选择游戏难度，以便获得适合自己水平的挑战
**验收标准**:
- [ ] 主菜单显示难度选择界面
- [ ] 简单模式: 怪物HP×0.7, 伤害×0.7, 道具掉落×1.5
- [ ] 普通模式: 当前数值
- [ ] 困难模式: 怪物HP×1.5, 伤害×1.5, 道具掉落×0.5
- [ ] 难度影响所有关卡
**技术约束**: 需修改 levels.json 和 monster_data.json 的数值加载逻辑
**依赖**: 无
**估时**: S (1-2天)
```

### 复杂度定义

| 等级 | 定义 | 预估时间 |
|------|------|---------|
| S | 改配置/改数值/小修 | 0.5-1天 |
| M | 新增单个功能模块 | 1-3天 |
| L | 跨模块功能/算法重写 | 3-7天 |
| XL | 架构级改动/新技术引入 | 1-2周 |

## 六、开发流程规范

### 1. 需求评审
- 每个需求必须有编号、描述、验收标准
- 复杂度 L/XL 的需求需要先写设计文档

### 2. 开发执行
- 修改代码前先 `grep` 确认所有关联位置
- 并行 agent 修改不同文件，避免冲突
- 每次修改后运行 `--headless` 验证编译

### 3. 测试验证
- 编译测试: `Godot --headless --quit`
- 功能测试: 运行游戏手动验证
- 回归测试: 确认修改没有破坏已有功能

### 4. 版本发布
- 每个功能完成打版本号 (vX.Y.Z)
- 版本号规则: 主版本.功能版本.修复版本
- 发布前必须通过编译测试

### 5. 文档同步
- 修改功能后同步更新对应 GDD
- 新增功能需先写需求文档再开发
- 重大决策记录到 notes.md
